What WebUSB Reveals That WebHID Does Not

The Tank Management page records the same kind of device log over WebHID. Comparing the two records for one physical device shows how much the choice of API changes what a site can learn.

Field WebHID WebUSB Why it matters
Vendor and product ID yes yes Identifies the model, not the unit
Product name yes yes Vendor-supplied string, not guaranteed unique
Manufacturer name no yes Attribution without relying on a vendor ID lookup table
Serial number no yes Identifies the individual physical unit, so it can correlate the same device across profiles, browsers and machines
Device and USB version no yes Firmware revision can narrow down a specific unit further
Class, subclass, protocol no yes Says what kind of device it is with no vendor knowledge
Interface and endpoint tree no yes Shows every function the device offers
HID report descriptors yes no The one area where WebHID is the richer source
Enumerate without a prompt granted only granted only Both return prior grants with no user gesture
List all attached devices no no Neither API can enumerate the bus

Where This Record Lives

The page writes three separate records, each with different survival characteristics:

  • usbDeviceRegistry in localStorage: one entry per distinct device, with first seen, last seen, a sighting count, and the full configuration tree. Survives browser restarts.
  • usbDeviceEvents in localStorage: a capped timeline of sightings, grants, and plug events. Survives browser restarts.
  • usbSessionDevices in sessionStorage: sightings for this tab only, discarded when the tab closes.

Because WebUSB reports a serial number, registry keys here name an individual unit rather than a model. Two identical label printers produce two separate entries, where the WebHID record on the Tank Management page would collapse them into one.

A fourth record is kept by the browser itself, not by this page. When a device is granted, the browser stores that permission in its own profile so the grant survives a reload. That is why devices can appear in the record above with no user action on this visit. Clearing the site record with the button above does not revoke the browser's grant, and revoking the permission in browser settings does not erase the site record. The two are independent, and they can disagree.

Limits worth noting: WebUSB cannot enumerate the bus. The chooser dialog sees every attached device, but the page only ever learns about the ones already granted plus the ones picked. The browser also refuses to let a page claim certain interface classes, including keyboards and mice, mass storage, smart cards, audio and video. Those devices can still be surveyed for identity, but not communicated with. Any interface in a blocked class is flagged in the configuration tree above.

Access note: the check guarding this page reads a flag out of localStorage in the browser. It keeps the page tidy for visitors, and it is not a security boundary. Anyone who can open developer tools can set that flag. Compare what the gate actually prevents against what it appears to prevent.
